### 1.18.0 已完成的判断（2026-11-25）

字段集 21 的同义核对在 Pixel 6 改写机上得到"3 对一致"，说明成对核对只能检验改写是否完整。字段集 22 改走三条与声明无关的通道，同一台机上立刻暴露两处不一致（内存三口径 12/12/7.44 GiB；`mt6985` 声明应有的核心与实测 `0xd05/0xd0b/0xd44` 无交集），而 GPU 字符串仍与声明一致。由此确定后续原则：

- **优先找"改写层没盖住的地方"**：`/proc` 节点、C 库调用、驱动自报字符串，比再读一个 `getprop` 有价值。
- **登记表要小且可追**：SoC→核心/GPU 映射只收有书面依据的型号，未登记记未确认；映射本身要能被复核，所以放在代码里而不是阈值配置里。
- **别名先于阈值**：`Mali-G715` 与 `Immortalis-G715` 是同一核，首版误报就出在这里。新加映射前先查同核别名。
- **构建产物比属性更硬**：1.19.0 的 `environment.overlayDeviceCodename` 取自 framework RRO 文件名，改机层改属性不会重建该文件；但它证明的是"镜像构建产品名"，不是物理机器型号，措辞必须停在"核对测试条件"。
- **内核写入值优于进程级改写**：字段集 24 的 `cpu.cpuCapacity`（内核调度器按实际核心类型写下的算力权重）与 `memory.cmaTotal`（内核启动时预留的连续内存池）都不是进程能伪造的读数——改机层 hook 的是 `Build`、`getprop`、`sysconf` 这些进程侧接口，不会重算内核的簇结构与板级预留。判定上采用"登记表反查"：实测命中**另一个已登记 SoC** 的 profile 即判冲突（正向识别），命中声明 SoC 自己的登记值判一致，两边都不在表内记未确认，不用"最接近的一项"去猜。
- **属性只在被改装的设备上按 UID 分裂，文件名始终是硬的**：字段集 25 的实测给出这条的边界，1.21.2 又用第二台机器把它收窄了。改装机 Pixel 6 上 `ro.boot.hardware.sku` 在 shell（`GR1YH`）与 `run-as`（`23078PND5G`）之间分裂，App 侧声明 SKU 与三个 overlay 候选全不匹配，证据串按设计退回 `sku:g9s9b,gb7n6,gr1yh` 并列形态；而**未改装的 MI 8 在两个 UID 下读到完全相同的值，且 `ro.boot.hardware.sku` 根本不存在（两边都读空）**。所以正确表述是「**被改装的设备上，属性按 UID 改写；未改装设备上两个 UID 一致**」——per-UID 改写是改机层行为，不是 Android 行为。`sku:` 只作旁证、不参与代号判定；代号仍由 `rro`／`vendor_dir`／`product_dir` 裁决。**把"声明值"当证据时，必须先问它在哪个 UID 下读到。**
- **登记表宁可留空，也不要猜**：`sdm845` 只登记了 label、cores（`0x802`／`0x803`）、gpu（`adreno`）与别名，**capacities 与 cmaMiB 故意留空**——内核 4.9 根本不暴露 `cpu_capacity`，`CmaTotal` 是设备树值不是 SoC 常量（MI 8 是 200 MiB，同 SoC 其它机型可能不同）。留空让这两条通道在该机型上判未确认，比填一个"看起来合理"的数字安全得多。新增登记会改变判定结果，所以画像规则随之 `/7` → `/8`。

产品验收仅使用 App 自行采集的证据。旧 ADB 对照只是独立历史，不参与评分，不要求复现「6 项」。下文为历史评估和长期备选，提到的旧候选、规则、实验命令或状态不覆盖本节。

建议分三步交付，每步都有可独立验收的结果。

1. **网络摘要一致性。** 两台手机各采 Wi-Fi 和移动数据，旧 Android 再覆盖电话权限授予和拒绝。手机预览、网页、导出的 LAN 报告使用同一份字段语义。旧 MI 8 报告只从原已保存字段展示注册 LTE，订阅制式保留未采。单小区带宽与频段、协商速率、订阅载波带宽分开展示。
2. **ROM 实验与复测。** 在现有设备历史中选择基线，给新采样关联同一实验。首个模板为 Wi-Fi 转蜂窝，记录权限、SIM 是否就绪、默认路由、系统联网验证和相对时间。蜂窝阶段先留本地，恢复内网后预览上传。比较两轮时能区分条件变化、持续异常和本轮恢复，JSON 用稳定用例键和报告引用供脚本复核。
3. **按测试目标选分支。** ROM 日常验收优先固定媒体片段的解码实验，两台设备可独立复测。硬件信任优先则先做服务器挑战验证原型，验收可信链、未知根、挑战重放和设备不支持四种结果。两条扩展均从单个可复现用例开始。

## A · 建议的默认节奏

1. **设备历史与归组治理。** 首版已在资产页实现同设备采样时间线、ROM/Android 与字段集提示、任选两份直达对比。接下来加实验标签、操作记录、合并影响预览和撤销；设计实验室资产码，显式完成跨重装关联，不启用隐式硬件识别。验收：同机跨安装历史连续、两部相同型号不会合并，误归组能还原。
2. **ROM 对比。** 先完成同一设备的前/后两个样本，再支持按机型、 Android 版本、字段集、权限和批次选择两组。分别展示静态项、会波动的动态项、归档缺项，以及有值率的分子分母；可锁定基线并导出可复现过滤条件。验收：旧版缺字段不计为 ROM 退化；报告从变化项能链接源字段、样本和来源。
3. **项目化工作流。** 已支持保存预期默认网络与解锁条件；App 复测准备区分采样时链路和当前授权。下一步把「刷机前/后」「Wi-Fi/蜂窝」「主卡/副卡」做成测试模板，记录真实采样的权限条件和 ROM，汇总影响范围后再考虑发布前检查。

## B · 采集路线：分层而不是只追求更多字段

- **普通应用层：** 优先补 Wi-Fi 带宽与标准、LTE/NR 载波归属、蜂窝接管、应用可见的 IPv4/IPv6 验证、可复现实验的最短步骤。严格区分活动链路、系统已验证联网、调制解调器状态与权限。验收：至少在 MI 8 和一台较新的双卡机实测，授权与未授权各跑一遍。
- **外部实验层：** 在同意下由独立桌面工具导入 ADB 诊断快照，标明不同时间与观察身份；在自维护 ROM 另行评估只读诊断服务，不提高普通应用权限。如同一字段两层不同，保留两份来源而不是覆盖。验收：可复现来源差异、输入有界、数据按白名单导入。
- **现场质量：** 将权限、网络、采样时效和错误码变成报告中的复测提示。离线情况下可只导出本地，后续自选上传；任何自动化不得偷偷上传。

## E · 安全证据与可信度

**0.20.0 后的实验顺序。** 给每项新检查先定义要回答的问题，再选采集方式。下一轮将 ROM 验收和环境识别分别做成可重复实验。

| 实验 | 方法 | 验收 |
| --- | --- | --- |
| 同一手机升级前后 | 固定 MI 8 和 ROM，选 0.18.1 归档与 0.20.0 新快照；对照采集器和字段集 | 新增字段可追溯到采集器，而网络、权限和 ROM 改变各有记录 |
| 技术能力回归 | 0.21 已实现固定 AVC 样片的本机首帧实测。下一步同一台手机刷机前后各跑三次，比较解码器选择和失败阶段 | 先验证同样片能否解出图像；若系统声明支持但实际失败，分别排查容器读取、解码器初始化和首帧输出 |
| 环境规则回归 | 已知原厂实机、自定义 ROM 实机、Android Emulator 分别建样本。每类测正常运行，并按需加入联网状态或调试器变化 | 按独立设备统计虚拟声明命中、证据不足和误报。已知模拟器缺少标记时记录规则未覆盖 |
| 证据强度升级 | 使用独立挑战验证原型对照登记的可信根、启动密钥和镜像策略 | 先覆盖有效、未知根、挑战重放、过期、未支持五类；认证结论带验证时间和策略版本 |

每项检查都应对应可执行的下一步。ROM 实验室需要定位回归。普通用户需要核对旧补丁和意外关闭的保护。各项结果保留读数、来源和适用范围。

0.18 已推进普通应用层的分区／组件基线、手动密钥保护自测与对应发布签名查证。下一次真实验收聚焦：MI 8 的 API 29 硬件级别降级显示；同机两次不刷机的稳定性；自有 ROM 预期更换单个分区时能否定位差异。之后再评估独立挑战、证书撤销和自有启动公钥登记；不把这一步写作已交付认证。

1. **已交付：** 启动链、SELinux、补丁时效、锁屏与加密、调试和配置一致性。缺项保留未知，自定义 ROM 的预期差异单列，不提供黑盒分数。
2. **已交付首版复测：** 仓库可保存命名基线和预期解锁条件；在安全页用基线比较新报告，查看归档覆盖差异及原始证据，并导出结构化结果。下一项是多条件实验模板（ROM、权限、网络）和同设备批次对比；先用两部现有测试手机跑同机刷机前后验收，再考虑自动回归门槛。
3. **需要高可信时：** 经同意开放独立的挑战/应答认证通道。先验证签名链、时间、重放与版本失败用例，再研究不同设备/ROM 的可用性。证明不可用与验证失败分开，普通报告保留不受影响。团队可在设备兼容优先与高可信优先之间选路线。

## C · 服务化路线

1. 上线前完成 HTTPS、管理员会话和设备上传凭证分离，区分只读、测试上传、资产管理和发布角色；审批 APK 发布并单独保管签名。可选回滚路径须满足 Android 包签名和版本要求。
2. 制定数据库与产物备份、恢复时限和操作记录。用测试环境恢复备份，并核对报告数量、样本散列、设备归组和当前发布包；ZIP 归档不充当备份。
3. 按真实仓库体量测 P95、并发导出和增长空间；先保留 PostgreSQL，规模确实需要时再预聚合、分区或接对象存储。观察项包括上传成功率、统计时延、队列阻塞和备份成功率。

## D · 开发者与智能体路线

- 先提供轻量命令行：验证报告契约、按条件导出、计算基线差异、生成复测清单。每次输出字段集、筛选范围、样本数和来源 ID。
- 配套字段字典与 JSON Schema：字段单位、状态原因、最低 API、权限和引入版本从同一配置导出；加入跨版本样本与契约 CI。
- 最后才引入本地或独立授权的分析助手：从缺项/回归提出待验证假设，每条结论带证据引用；默认输入脱敏、只读，禁止自动归组、删报告或发布版本。

**取舍建议：** A 先做，B 并行跑小规模真机验证，C 在服务器部署前作为门槛，D 从字段字典开始而不急于接模型。若近期重点改成真机采集广度、服务器交付或自动化接入，可分别优先选 B、C、D。

## 1.8.0 之后的采集扩展候选（2026-11-24）

字段集 17 之后，继续加字段的边际收益开始下降。先按「能不能回答测试团队的问题」排序，而不是按「还能读到什么」排序。

| 候选 | 能回答什么 | 成本与风险 | 建议 |
| --- | --- | --- | --- |
| 分区指纹属性（`ro.system/vendor/product/odm/bootimage.build.fingerprint`） | API 29 以下机型也能对照分区构建；补齐 `Build.getFingerprintedPartitions` 的版本缺口 | 属性在不同 ROM 上可读性不一；值较长，需要长度与字符白名单 | **下一轮优先**，先在两台现有手机上核对可读性 |
| 传感器按类型计数摘要 | 传感器数量少但类型异常的环境 | 现已有 `sensors.count` 与 `typeWakeupSummary`，增量小 | 观察，不急着加 |
| 热区温度（`/sys/class/thermal`） | 与 `PowerManager` 热分级交叉核对 | 多数 ROM 对普通应用拒绝，且分级已能回答是否过热 | 不作为独立字段；若加只作可选线索 |
| 匿名可执行映射统计 | 更细的用户态注入线索 | 误报与隐私争议都高，无法给出稳定阈值 | 只保留现有的文件路径命中 |
| 密钥认证证书链 | 真正的硬件证明 | 需要独立信任根、挑战协议与服务器角色，成本最高 | 走既有「独立挑战」路线，不并入普通采集 |
| `MediaDrm` 设备唯一标识 | 区分设备个体 | 属于可标识设备的标识符，与本仓库的隐私边界冲突 | **不采纳**；只保留保护级别与厂商/版本 |
| 其他应用清单、运行进程、无障碍内容 | 更多环境证据 | 需要高权限或触碰用户隐私，且无法在普通应用内合法获得 | **不采纳** |

优先顺序：先在 Pixel 6 与 MI 8 上完成 1.8.0 的真机复测（SELinux 推断、TracerPid、映射与挂载线索、属性快照可读键），再决定是否把分区指纹属性并入字段集 18。没有真机证据之前，不建议继续扩张字段集。

## 1.9.0 之后：机器码与还要不要继续扩字段（2026-11-24）

**机器码有帮助，但不是身份证明。** 它把设备描述拆成商品、硬件、ROM 三个分量，能回答：同一资产多次采样是否稳定、刷机或 OTA 改了哪一层、同型号之间是否同码、后台能否用同码发现“同配置不同设备”或“同设备不同配置”。它不能回答：这台设备是否原厂、是否被改机。真机上已经出现 App 与 shell 两套自洽身份，正好说明机器码只能编码“某个观察者看到的配置”。

**还需要采集更多信息吗？** 现阶段优先级从“加字段”转向“加一致性规则”，因为字段数量已经不是瓶颈：

| 候选 | 价值 | 建议 |
| --- | --- | --- |
| 身份一致性规则：同一份报告内 Build 型号/主板/SoC/显示/RAM 是否互相矛盾；跨来源型号/主板不一致时提示 | 高：本轮真机案例就是这类冲突 | **下一步做规则，不加字段** |
| `Settings.Global.BOOT_COUNT` | 中：判断是否短时间内反复重启/刷机 | 先在两台机器验可读性再决定 |
| Android 8/9 的分区属性回退真机样本 | 中：当前只有静态与契约核对 | 需要一台旧设备 |
| `Build.VERSION.MEDIA_PERFORMANCE_CLASS` | 低：两台测试机都未声明 | 观察，不急着加 |
| 内核物理内存 `sysconf(_SC_PHYS_PAGES)` | 低：与 `ActivityManager.totalMem` 口径不同，容易误导 | 不加 |
| 唯一标识（IMEI/序列号/MAC/DRM 唯一 ID）、其他应用数据 | 与隐私边界冲突，且需要高权限 | **不采纳** |

结论：字段集 18 之后先补“身份一致性”与“旧 API 分区”两块，再考虑新字段。没有真机证据前不再扩字段集。

## 1.10.0 之后：身份漂移与下一步（2026-11-24）

本轮按推荐顺序完成：字段集 19 身份声明 → App 内部三对一致性 → 跨来源并列 → 同资产历史身份漂移（`identityHistory`）→ 隔离栈上传验收。8/9 分区回退补了纯函数单测，仍缺真机样本。

| 下一步 | 为什么 | 建议顺序 |
| --- | --- | --- |
| 资产级身份冲突汇总（多资产同码/多身份预警） | 单份报告只看得到自己；仓库层才能发现同一资产反复变化或同码多设备 | 先做只读统计，不改告警阈值 |
| Android 8/9 分区属性真机样本 | 当前只有单测与契约，没有真机验证 | 需要一台旧设备 |
| 身份冲突的产品口径（是否提升告警级别） | 现在只给「请核对」，是否升级需要产品定义 | 讨论后再改规则 |
| `BOOT_COUNT`、媒体性能等级 | 候选新字段，价值中等 | 先验可读性，不急着加 |
| root 观察通道 | 只在明确需要策略正文/其他应用数据时才有意义 | 保持 opt-in 外部文件，不并入 App |

结论：字段与规则的主要链路已经闭环，接下来优先做仓库级统计与真机补样，而不是继续加字段。

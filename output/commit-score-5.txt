feat(score): field set 26 adds ro.boot.qemu, score /5 fixes three defects

一、本提交做了什么

两件事：给采集契约加一个字段（字段集 25 → 26），给评分体系修三个缺陷（sigmark-score/4 → /5）。
两件事都来自同一台真实设备：雷电 LDPlayer 9 首次用新版 APK 采集后暴露出来的问题。

二、为什么加 system.bootQemu

雷电 LDPlayer 9 的 getprop 实测：

    ro.boot.qemu    = 1        ← 自己承认是 QEMU
    ro.kernel.qemu  = （空）    ← 被清掉了

它清掉了最经典的那条，却漏了这一条。一条 getprop 就能判定，而我们从没采集它
（全仓非测试代码零命中）。这不是"判据不够强"，是这条判据从来没进系统。

四、字段集 25 → 26 的五层锁步

加一个字段要同时动五处，缺一层测试就红：

    1. Android 采集      DeviceCollectors.kt:139  declaredProperty("bootQemu", ...)
    2. Android 投影      LanDetails.kt:14 / :30  两处 system 组各加 bootQemu
    3. Android 版本      LanReport.kt:19          LanFieldSetVersion 25 → 26
    4. Go 白名单         protocol.go:96           {"system", "bootQemu", 26}
    5. Go 上限           protocol.go              新增档位 >= 26 → maxFields 260
    6. 字段字典          field_dictionary.go      latestFieldSet 26, dictionaryVersion /17
    7. 契约断言          protocol_test.go         静态键数 235 → 236

maxFields 的公式是 235 + 新增固定键数 + 24，本档写 236 + 24 = 260。
不写死数字，下次加字段只需新增一档，不动 259/260 这两行。

新增 fixture app/src/test/resources/lan-projection-v26.txt（236 行，UTF-8 无 BOM，
CRLF，Ordinal 排序，system.bootQemu 落在 bootHardware 与 bootloader 之间）。
projectionMatchesSharedLanRegistry 比对投影键集与这份 fixture，是第五道闸门。

五、评分体系的三个缺陷

缺陷 1：决定性命中吞掉了 value

雷电报告修复前 value 是空的，三个轴分也全是空的。coverage 0.73 高于地板 0.5，
按 R8 该出数字。

判定：bug。R10"声明轴盲 → 不出版数字"没有区分"盲且无人兜底"和"盲但已被决定性
cap 定了档"。后者的全部依据——"别为一个没人看过的画面出版一个舒服的结果"——在
band 已经被钉在 D 之后不再成立；而 F5 本来就要求决定性命中保留 value 当排序键。

修复：抑制条件改为 declarationBlind && !Decisive。
R8（coverage 低于地板）和 weights == 0 仍然无条件吞数字，那里"没有数字"本身就是结论。

缺陷 2：behavior 轴分与它自己的账本不符（三个里最严重）

存档报告 behavior 轴印 85（= 100 − 15），但它自己的 deductions 是 35 + 15 = 50。

根因：STRUCTURAL_VIRTUAL_EVIDENCE 这条扣分是在 finalizeScoreAxis 之后才 append 的，
那 35 分从来没进过轴分。它只贡献了 cap，没贡献扣分。

这个 bug 在真机上永远暴露不了——真机不命中结构通道。只有模拟器数据能照出来。
这是"测试样本必须包含攻击样本"的活例证。

修复：finalizeScoreAxis 移到结构通道 append 之后。顺带修掉"三轴可见分数加权 ≠
出版 value"的不可复算问题。

效果：behavior 85 → 50，总分 91 → 71。
    (85×35 + 100×25) / 60 = 91.25
    (50×35 + 100×25) / 60 = 70.83 → 71

缺陷 3：FRESH_BOOT_ON_AGED_ROM 在模拟器上误报 −12

雷电 initialSdk = 28（Android 9 代），镜像是 Android 14。规则判定"新启动跑在老代
设备上"可疑，扣 12 分。但模拟器镜像的 first_api_level 与镜像 API 不一致是固有特征，
不是攻击行为。

修复：虚拟化已被独立通道确认时不再计分。新增 virtualEvidenceConfirmed()：
virtual_build_markers 标签 hit 或结构通道命中，任一即真。扣分与抑制读同一份证据。

两条关键约束：
  - 单向。只看"虚拟化是否已被独立通道确认"。声称自己是模拟器要付 35 分 + D 档，
    没有攻击者能靠这个逃掉。
  - 抑制的是定价，不是可判性。decided 仍为 1、coverage 仍 1.00。否则模拟器的
    coverage 会被悄悄拉低，可能掉到地板以下——那就变成借修复之名改形状了。

这是"一因一果"原则的延伸：同一个"这是模拟器"的事实不该被计两次。

六、为什么升到 sigmark-score/5

两个缺陷都改变计分行为，不只是缺陷 3：
  - 缺陷 3 直接改计分：usage 轴 88 → 100。
  - 缺陷 2 改计分：behavior 85 → 50，总分 91 → 71。影响比缺陷 3 大得多。
  - 缺陷 1 严格说是形状变更（null → 数字），但它把"两个 D 能不能排序"从不能变成能。
    前端如果按 value === null 分支渲染会走错路，所以一起升。

profileVersion 不动（标签层没变）。

八、arm64 结论修正：从"未测"改成"硬性不支持"

上一版台账写"未测（工作量问题）"。这轮真下载了 3GB arm64 镜像并启动，结论不同：

    FATAL | Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator
            on x86_64 host. System image must match the host architecture.

5 秒内 FATAL 退出。Windows x86_64 上的 emulator 只提供 QEMU2 x86_64 版本，没有
ARM 转译层（Apple Silicon 才有，那边宿主本身就是 arm64）。不是配置问题、不是缺参数。

一个容易混的点：两台真机都是 arm64，SigMark 在 arm64 上跑得通（已验证）。没验证的
只是"arm64 模拟器启动多慢"，而这个数字在 x86 宿主上不存在。

环境已清理：AVD 删除，3GB 镜像 uninstall。

九、一处自我纠正：adb 读数不等于产品能力

本轮一度把 Pixel 6 的 boardPlatform 记成 gs101。实际报告里是 mt6985，三份一致。

    adb shell getprop ro.board.platform  →  gs101
    App 采集到 system.boardPlatform     →  mt6985

SigMark 是 App，产品形态是普通应用在普通用户手机上采集。adb / shell 读数只是开发期
的辅助观察，不是产品能力。任何判据、样例、结论都必须以 App 视角的采集结果为准。

这条已写进 docs/VIRTUALIZATION-MATRIX.md §〇 作为铁律。
